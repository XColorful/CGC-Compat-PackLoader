## 根因

26.3 把 `PackFormat` 从单个 int 改成了 `(major, minor)`，判定逻辑在 `PackCompatibility.forVersion`：

```java
} else if (packDeclaredVersions.maxInclusive().compareTo(gameSupportedVersion) < 0) {
    return TOO_OLD;
```

而 `DetectedVersion.createBuiltIn` 给出的当前版本是：

| | 26.3 当前版本 | 我们的合成元数据 | 结论 |
|---|---|---|---|
| 资源包 | `PackFormat.of(97, 1)` | `PackFormat.of(97)` = `(97, 0)` | `(97,0) < (97,1)` → **TOO_OLD** |
| 数据包 | `PackFormat.of(121, 0)` | `PackFormat.of(121)` = `(121, 0)` | 恰好相等 → COMPATIBLE |

`PackFormat.of(major)` 的 minor 是 0，正好落在当前 minor 之下——这解释了为什么只有资源包被标旧版本，数据包没事（`DATA_PACK_FORMAT_MINOR` 恰好是 0），但那只是巧合，minor 一抬同样会坏。

## 改法

[FallbackMetadataPackResources.java:61](core/src/main/java/dev/xcolorful/cgccompat/packloader/core/resource/FallbackMetadataPackResources.java:61) 改用 `PackFormat.of(major).minorRange()`，声明成 `[(97,0), (97, MAX_VALUE)]`：

```java
PackFormat.of(packType == PackType.SERVER_DATA
        ? CgccPackLoader.DATA_PACK_FORMAT
        : CgccPackLoader.RESOURCE_PACK_FORMAT).minorRange()
```

覆盖整个 major 而不是钉死当前 minor。理由是合成元数据本来就不描述具体内容版本，而 `CgccPackLoader` 里那句注释的原意就是「不要每装一个包都多点一次提醒」——钉死 minor 的话原版抬到 97.2 又会重新变旧。

## 同一判定下的第二处，需要你定

`core/src/main/resources/pack.mcmeta` 的 `${pack_format}` 来自 [gradle.properties:38](gradle.properties:38) 的 `pack_format=15`。26.3 里单个 int 的 `pack_format` 已经是遗留字段（只允许 ≤ 64 资源 / ≤ 81 数据），会解析成 `[(15,0),(15,0)]`，同样判 TOO_OLD。

26.3 的写法是按 major 声明：

```json
"min_format": 97,
"max_format": 97
```

`TOP_CODEC` 读单个大数时 minor 取 `Integer.MAX_VALUE`、`BOTTOM_CODEC` 取 0，所以这么写正好等价于「整个 major」，和我们上面用的是同一个语义。数据包侧对应 121。
